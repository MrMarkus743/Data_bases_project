# ГРУППОВЯ РАБОТА ПО ДИСЦИПЛИНЕ «БАЗЫ ДАННЫХ»

## Общие положения

Групповая работа выполняется в течение первого семестра (3 семестр) и является сквозным проектом, закрепляющим всю практику дисциплины.

**Цель работы:** спроектировать и реализовать базу данных для выбранного профильного кейса, охватывающую все этапы: от анализа предметной области и карты данных до физической реализации, аналитических запросов и программного доступа.

**Формат сдачи:** репозиторий в GitFlic/GitHub/архив со следующей ориентировочной структурой:

```
/
├── docs/
│   ├── analysis/
│   │   ├── data_map.md          # Описание предметной области и карта данных
│   │   ├── access_matrix.md     # Матрица доступа и требования к защите
│   │   └── data_flow.png        # Схема потоков данных
│   └── diagrams/
│       └── er_diagram.png       # ER-диаграмма
├── sql/
│   ├── schema.sql               # DDL-скрипт (таблицы, ограничения, индексы)
│   ├── seed.sql                 # Тестовые данные (или Python-скрипт генерации)
│   ├── queries.sql              # Аналитические запросы
│   ├── triggers_functions.sql   # Функции, процедуры, триггеры
│   └── roles.sql                # DCL-скрипты (роли, GRANT/REVOKE)
├── python/
│   └── db_access.py             # Скрипт подключения и выгрузки данных
├── README.md                    # Описание проекта, результаты EXPLAIN ANALYZE
└── report.pdf                   # Пояснительная записка
```

**Общие требования ко всем вариантам:**

1. В БД должно быть минимум **8 таблиц**.
2. Должны быть реализованы ограничения: `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `CHECK`.
3. Должен быть минимум **3 индекса**, напрямую участвующие в запросах (B-tree, GIN или BRIN — по выбору, в зависимости от задачи).
4. Должен быть минимум **1 VIEW** и **1 MATERIALIZED VIEW**.
5. Должна быть минимум **1 функция или процедура** на PL/pgSQL.
6. Должен быть минимум **1 триггер** (BEFORE/AFTER/INSTEAD OF).
7. Должны быть созданы **минимум 3 роли** с разными правами доступа.
8. Должен быть **Python-скрипт** для подключения к БД и выгрузки данных в pandas.
9. Должны быть выполнены **EXPLAIN ANALYZE** для минимум 3 запросов (до и после создания индексов).


## Особенности приема работы
Вы делитесь на группы по 3 человека: аналитик, администратор, разработчик.
Каждый из вас выполняет свою часть. Общий результат работы вы сохраняете в своем репозитории. Перед сдачей работы вы открываете доступ к репозиторию для меня.
На защите вы будете отвечать на вопросы **НЕ ПО СВОЕЙ РОЛИ**. Например, аналитика я буду спрашивать о том, что сделал разработчик или администратор. И так для всех троих.

# -----------Роль: аналитик---------------
### Этап 0. Выбор датасета
Необходимо взять крупный датасет (минимум на миллион строк в общем), описывающий какую-то предметную область. Ресурсы:
- https://huggingface.co/datasets
- https://www.kaggle.com/datasets
- https://data360.worldbank.org/en/search
- https://data.imf.org/en/Datasets#t=coveo117bcfc4&sort=%40idata_publication_date%20descending

### Этап 1. Анализ предметной области и карта данных (ПР №1)
Потребуется: датасет, pandas, python, навыки создания и выгрузки дампа СУБД.
**Задание:**

1. **Описание предметной области** (5–10 предложений):
   - Какую бизнес-область описывает датасет?
   - Какие процессы автоматизируются?
   - Кто пользователи системы?
   - Какие решения принимаются на основе данных?

2. **Выделение сущностей и атрибутов** (минимум 8 сущностей):
   - Нормализуйте датасет на таблицы.
   - Для каждой сущности укажите: назначение, ключевые атрибуты, первичный ключ.
   - Создайте индексы, PK, FK, ограничения, обоснуйте выбор типов данных.
   - Отметьте, какие атрибуты обязательные, уникальные, ссылочные.

3. **Карта данных** (оформите в виде таблицы с колонками):
   - Источник данных
   - Сущность
   - Атрибут
   - Тип данных
   - Пример значения
   - Обязательность (Да/Нет)
   - Уникальность (Да/Нет)
   - Примечание (ПДн / коммерческая тайна / открытые)

4. **Классификация данных:**
   - Определите, какие атрибуты относятся к **персональным данным** (в контексте 152-ФЗ).
   - Определите, какие атрибуты относятся к **коммерческой тайне**.
   - Определите, какие данные являются **открытыми**.

5. Разработайте **DDL-скрипт** (`schema.sql`), который создаёт:
   - Все таблицы с подходящими типами данных PostgreSQL.
   - Ограничения: `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `CHECK`.
   - Индексы (минимум 1 B-tree; при необходимости — GIN или BRIN).

**Задание: разграничить доступ к данным БД**

1. **Список ролей пользователей** (минимум 4 роли):
   - Например: кредитный аналитик, оператор, кредитный комитет, администратор БД.
   - Для каждой роли опишите её функции в системе.

2. **Матрица доступа** (оформите в виде таблицы с колонками):
   - Сущность
   - Категория данных (ПДн / коммерческая тайна / открытые)
   - Роль
   - Разрешённые операции (SELECT, INSERT, UPDATE, DELETE)
   - Запрещённые операции
   - Основание ограничения (ссылка на закон или бизнес-правило)

3. **Требования к защите данных:**
   - Какие поля нужно обезличивать при выгрузке для аналитиков?
   - Как организовано журналирование (какие действия и в каких таблицах должны логироваться)?
   - Какие данные требуют шифрования?
   - Какие требования к резервному копированию и срокам хранения данных?

4. **Проект ролей PostgreSQL:**
   - Перечислите названия ролей.
   - Опишите, какие привилегии будут выданы каждой роли (на уровне схемы, таблиц, представлений).
   - Обоснуйте, почему выбраны именно такие права.

### Этап 3. Аналитические запросы и витрина данных

**Задание:**

Разработайте **6-8 аналитических SQL-запросов**, решающих следующие бизнес-задачи (реализуйте их в файле `queries.sql`). Для каждого запроса укажите комментарий с пояснением цели.

**Обязательные запросы:**

1. **Запрос с CTE и JOIN:** Вывести ТОП-5 заемщиков по объему чистой прибыли за последний год с указанием общей суммы непогашенных кредитов.

2. **Запрос с оконными функциями или подзапросами:** Найти все кредитные договоры, где сумма обеспечения (залога) меньше 80% от суммы кредита.

3. **Запрос на ваш выбор** (должен использовать `JOIN` и `GROUP BY`).

5. **Создание и работа с материализованным представлением** для витрины данных, объединяющей информацию о заемщиках, их финансовых показателях, кредитной нагрузке и уровне риска. Напишите запрос для создания `MATERIALIZED VIEW` и команду его обновления (`REFRESH`).


# -----------Роль: администратор---------------
### Этап 4. Серверный код (функции, процедуры, триггеры)

**Задание:**

Реализуйте в файле `triggers_functions.sql` следующие объекты:

1. **Функция или процедура** на PL/pgSQL, которая:
   - Принимает идентификатор заемщика.
   - Рассчитывает уровень кредитного риска (например, HIGH/MEDIUM/LOW) на основе соотношения долга к выручке.
   - Возвращает строку с уровнем риска.

2. **Триггер `BEFORE INSERT OR UPDATE`** на таблицу кредитных договоров, который:
   - Проверяет, что сумма кредита не превышает 50% от выручки за прошлый год.
   - В случае нарушения выбрасывает исключение с понятным сообщением.

3. **Триггер аудита** (журналирования) для таблиц, содержащих персональные данные или коммерческую тайну:
   - При `INSERT`, `UPDATE`, `DELETE` записывает в таблицу `audit_log` информацию: кто, когда, какая таблица, какая операция, старые и новые данные (в формате JSON).

- Обоснуйте создание **каждого** триггера, продемонстрируйте реализацию аудита.
- Приведите SQL запросы, показывающие **подробную статистику** по использованию таблиц: самые частые и ресурсоемкие запросы, использование индекса, использование диска. Расскажите, какие расширения PostgreSQL вы для этого устанавливали. Будьте готовы объяснить каждый из запросов.

### Этап 5. Роли и права доступа (DCL)

**Задание:**

Создайте файл `roles.sql`, в котором:

1. Создаются минимум 3 роли (например: `credit_analyst`, `credit_operator`, `loan_committee`).

2. Назначаются права доступа:
   - На схему (`USAGE`).
   - На таблицы и представления (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
   - С учётом разделения ПДн и коммерческой тайны (например, аналитик видит только обезличенные данные).

3. Продемонстрируйте, что запрещённые операции действительно недоступны (можно описать в отчёте или показать скриншоты).
