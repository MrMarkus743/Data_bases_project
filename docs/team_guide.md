# Внутренний регламент и руководство команды проекта

Данный документ описывает текущее состояние инфраструктуры проекта, зоны ответственности участников команды и регламент совместной работы в Git и GitHub.

---

## 1. Что уже подготовлено и настроено

Базовая инфраструктура проекта развёрнута и готова к параллельной работе:

1. **Структура репозитория:**  
   Создан каркас каталогов по требованиям ТЗ:
   * `docs/` — аналитика, схемы и регламенты;
   * `sql/` — DDL-миграции, серверная логика (PL/pgSQL), скрипты прав доступа;
   * `python/` — ETL-скрипты пакетной загрузки, валидация данных.
2. **Изоляция данных и окружения (`.gitignore`):**  
   Настроена фильтрация: виртуальное окружение `venv/`, локальные дампы, служебные файлы IDE и тяжёлые файлы датасетов (`*.csv`, `*.xlsx`, папка `data/`) изолированы и не попадают в удалённый репозиторий.
3. **Защита главной ветки (`main`):**  
   Ветка `main` заблокирована настройками безопасности:
   * Прямой пуш (`git push origin main`) запрещён.
   * Все изменения вливаются исключительно через механизм Pull Request после рецензирования.
   * Обращение к ветке `main` предусмотрено только на финальном этапе перед итоговой сдачей проекта. Локальное переключение на `main` и внесение правок в процессе текущей разработки исключены.
4. **Интеграционная ветка (`develop`):**  
   Создана и назначена основной рабочей веткой по умолчанию. Все функциональные ветки формируются от `develop` и объединяются с ней.
5. **Проектная доска (GitHub Projects):**  
   Настроена канбан-доска с ролевой разметкой (`Data Analyst`, `DBA`, `Developer`) для распределения и контроля задач.

## 3. Регламент работы с Git (Жизненный цикл задачи)

Базовый принцип: **одна задача — одна изолированная ветка**. Прямое внесение изменений в ветки `develop` и `main` исключено.

```text
[develop] ──> создание ветки ──> фиксация коммитов ──> git push ──> Pull Request ──> [develop]
```

### Шаг 1. Актуализация рабочей ветки
Перед началом работы над задачей выполняется синхронизация локальной ветки `develop` с удалённым репозиторием:

```powershell
# Переключение на основную рабочую ветку
git checkout develop

# Получение актуального состояния из репозитория
git pull origin develop
```

### Шаг 2. Создание изолированной ветки
Создание новой ветки выполняется строго от актуальной ветки `develop`:

```powershell
# Создание ветки и автоматический переход на неё:
git checkout -b <префикс>/<краткое-название-задачи>
```

Стандартизированные префиксы веток:
* `docs/...` — документация, схемы, регламенты и отчёты;
* `sql/...` — скрипты схемы, хранимые процедуры, триггеры и роли;
* `python/...` — модули загрузки, тесты и скрипты валидации данных.

### Шаг 3. Внесение изменений и фиксация коммитов
Работа с кодом и документацией выполняется в рабочей среде. Изменения фиксируются атомарно:

```powershell
# Проверка изменённых файлов
git status

# Добавление целевого файла в индекс
git add docs/analysis/data_map.md

# Создание коммита по стандарту Conventional Commits
git commit -m "docs(analysis): draft initial data map and attributes"
```

### Шаг 4. Публикация ветки в удалённом репозитории
После завершения локального этапа ветка отправляется на GitHub:

```powershell
git push -u origin <название-ветки>
```
*(Параметр `-u` используется только при первой отправке новой ветки, при последующих вызовах достаточно `git push`).*

### Шаг 5. Оформление и рецензирование Pull Request (PR)
1. На странице репозитория на GitHub инициируется создание запроса кнопкой **Compare & pull request**.
2. **Проверка целевой ветки:**  
   Веткой слияния назначается строго **`base: develop`** (`compare: <название-ветки>`). Слияние в `main` заблокировано.
3. Формируется заголовок по стандарту Conventional Commits с описанием внесённых изменений.
4. В блоке **Reviewers** назначаются участники команды для проведения ревью кода.
5. После проверки и получения подтверждения (Approve) выполняется операция **Merge pull request**.

## 4. Стандарт сообщений коммитов (Conventional Commits)

В проекте принят стандарт **Conventional Commits** для обеспечения прозрачности и структурированности истории изменений.

### Формат сообщения
```text
<тип>(<область>): <краткое описание действия>
```

1. **`<тип>` (Type) — категория изменений:**
   * **`feat`** — добавление функционала, таблиц, процедур, скриптов загрузки;
   * **`fix`** — исправление ошибок в DDL, процедурах, триггерах или коде;
   * **`docs`** — создание и корректировка документации, файлов `.md`, регламентов;
   * **`refactor`** — переработка структуры без изменения внешнего поведения и логики;
   * **`style`** — правки форматирования (отступы, пробелы, регистр ключевых слов SQL);
   * **`chore`** — служебные задачи (`.gitignore`, обновление `requirements.txt`).

2. **`(<область>)` (Scope) — уточнение затрагиваемого модуля (опционально):**
   * `(schema)` — DDL-структура и ограничения таблиц;
   * `(analysis)` — аналитические материалы, 152-ФЗ, матрицы доступа;
   * `(triggers)` — серверная логика и процедуры PL/pgSQL;
   * `(roles)` — права доступа DCL и роли;
   * `(loader)` — ETL-скрипты пакетного импорта на Python.

3. **`<краткое описание>` (Description):**
   * Составляется на английском языке со строчной буквы;
   * Формулируется в повелительном наклонении (`add`, `update`, `fix`, `create` вместо `added` или `fixes`);
   * Точка в конце строки не ставится.

**Примеры корректных коммитов:**
```text
docs(analysis): add data map draft with privacy flags
feat(schema): create initial tables with constraints
fix(schema): correct foreign key reference in contracts
feat(triggers): implement audit log trigger with jsonb
feat(loader): add chunk-based ingestion in python
chore: update gitignore for large datasets
```

## 5. Регламент безопасности и разрешение нештатных ситуаций

1. **Ограничение на размер файлов:**  
   Запрещено включение в коммиты файлов датасетов и дампов размером более 50 МБ (`.csv`, `.xlsx`, `.zip`, `.gz`). Хранение данных осуществляется локально в каталоге `data/` с обязательной изоляцией через `.gitignore`.
2. **Запрет деструктивных операций:**  
   Использование флага `--force` (`git push --force`) строго запрещено для предотвращения перезаписи истории коммитов.
3. **Синхронизация при обновлении интеграционной ветки `develop`:**  
   Если в ветку `develop` внесены изменения другими участниками, подтягивание актуального кода в текущую ветку выполняется командой:
   ```powershell
   git pull origin develop
   ```
   В случае конфликтов строк выполняется выбор корректных блоков кода в редакторе с последующим сохранением.
